# ADR 0018: Public demo mode

Status: accepted (2026-10-15)

## Context
Recruiters and hiring managers should be able to open one public link and click through the whole product. The deployed paths sit behind Cloudflare Access, and dev sign-in works only on localhost. A public link means untrusted visitors on the operator's Workers Free account, which four other repositories share: no model may be called, no real data path may be reachable, every visitor's actions must stay private to that visitor, and cost and storage must be bounded by arithmetic rather than hope.

## Decision
1. **A third auth mode.** `SS_AUTH_MODE=demo` is accepted only with `SS_PUBLIC_DEMO=1` and the secret `SS_DEMO_SIGNING_KEY` (base64 of at least 32 random bytes); `SS_PUBLIC_DEMO=1` is refused with any other auth mode. Demo mode also refuses every real data path: a data mode other than `fixtures`, the BigQuery variables and key, `SS_LLM=workers-ai`, the AI Gateway variables and token, an `AI` binding, runner and MCP tokens, Access variables and role bindings. When any rule fails, `parseConfig` throws and the Worker answers 503 to every request. Engine jobs complete inline from the committed job fixtures; the model provider is `recorded`.
2. **Sign-in.** A landing page explains the demo in two sentences; the visitor picks one of the seven synthetic principals (default People Analytics Lead). `POST /demo/session` creates a sandbox and sets the cookie `__Host-ss_demo` (`HttpOnly; Secure; SameSite=Strict; Path=/`, no `Domain`): `v1.<payload>.<mac>`, where the payload holds the principal ID, the sandbox ID, issued and expiry times, and the MAC is HMAC-SHA256 under a key derived by HKDF from the signing key. Every request verifies it with a constant-time comparison; the expiry is at most 4 hours after issue and never later than the sandbox's. Roles and scopes come from `policy/` on the server, never from the cookie, so editing the payload cannot raise a role. `POST /demo/role` re-issues the cookie for another principal in the same sandbox with the same expiry; `POST /demo/reset` starts a fresh sandbox and retires the old one. The `__Host-` prefix makes a browser refuse the cookie unless this host sets it, so another Worker on the account's workers.dev subdomain cannot plant a session (its own sandbox, where it would read what the visitor does) for the demo; a request that carries two session cookies is refused.
3. **Isolation.** A sandbox ID is 20 base32 characters (100 random bits). All mutable state lives in the WorkspaceAgent `sbx-<id>`: runs and the published pointer, reviews, approvals, both audit chains, routine and held-run state, engine jobs, results, drafts, traces and memory writes. Chat history lives in AnalystAgent `an_` + HMAC of the sandbox and principal IDs. Workflow instance IDs carry the sandbox name and the workflow only talks to the agent that started it. Each sandbox starts from the committed demo state (API fixtures, recorded turns, recorded Lab sessions), bundled read-only. An alarm at the expiry destroys each sandbox object (`deleteAll`); a sandbox object woken after that (a late workflow step) seeds nothing and destroys itself two minutes later.
4. **Off in demo mode (404):** `/mcp`, `/dev/*`, `/api/dev/*`, `/internal/*` (runner protocol and fixture jobs), live LLM providers, Workers AI, AI Gateway and the engine.
5. **Chat.** Recorded Qwen3.6-27B turns replay for the recorded questions; any other question gets the deterministic stub (one tool chosen by rules, a template answer from its result, no model), and the answer's chip says which. The provenance line names "the author's laptop".
6. **Caps** (constants in `src/shared/demo/budget.ts`): 3 new sandboxes per client per hour, 15 per UTC day overall, 10 live sandboxes, 300 requests per sandbox per minute and 600 request units per sandbox lifetime, one routine run per sandbox, request bodies of at most 8 KiB, questions of at most 500 characters, reasons of at most 300 (checked by the HTTP route and again inside the agent before anything is written), WebSocket frames of at most 64 KiB, 20 per minute and 40 in the life of a connection. Over a cap the answer is 429 or 503 with "The demo is busy, try again later" and `Retry-After`; a sandbox that has spent its units says so and offers a fresh one. Creation counts live in one `DemoGate` Durable Object (SQLite), keyed by an HMAC of the client address (an IPv6 address by its /64, since one subscriber can hold a whole /64; never the address itself) and pruned after 2 days; the daily and live counts are for the current signing key only (a fingerprint derived by HKDF), so rotating the key frees the gate at once. The per-minute window of requests is kept in memory in the sandbox object; the lifetime count is reserved in SQLite ahead of use in blocks of 25 units, so an evicted object never undercounts. The Worker remembers, per isolate, a sandbox that answered spent, ended or rate limited, and refuses it again without a Durable Object request.
7. **WebSocket frames.** A frame guard runs before the agents SDK on both agents. Its counts live in the connection's attachment, so hibernation does not reset them. The SDK persists what a client sends before any of StaySignal's code runs, so the guard decides what it may receive: on a sandbox's WorkspaceAgent connection nothing (it only receives state; the callable actions also refuse in a sandbox, because a read-only connection blocks only `setState`, not RPC); on the AnalystAgent a chat request, a cancel and the stream-resume handshake only. A chat request spends its 18 units before anything is stored and is rewritten to the server's own history plus the visitor's one new question; a refused one is answered on its own stream and stores nothing. An upgrade spends 2 units, and `/agents-ws/*` forwards only a well-formed upgrade (`GET`, a `Sec-WebSocket-Key`, version 13) from this origin; anything else is refused before it spends units. A turn takes its question from its own admitted request: turns run one at a time, so a question sent while another turn runs is stored before that turn's answer.
8. **Same origin only.** Other Workers on the operator's account share its workers.dev subdomain, so their pages are the same site as the demo and a SameSite cookie goes with their requests. Every request to the Worker's demo routes, WebSocket upgrades included, is therefore refused (403) before any Durable Object request when a browser says another origin or site started it: an `Origin` that is not this exact origin (scheme, host and port), or `Sec-Fetch-Site` `cross-site` or `same-site`. Reads are covered too, since a navigation or an image on another page would spend the sandbox's units. A request with neither header is not a browser's and carries only its sender's own cookie, so it passes. Every response the Worker makes carries `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` and `Cache-Control: no-store`; the static assets get from `public/_headers` a policy of this origin only (`connect-src 'self'` covers the app's own sockets) with `frame-ancestors 'none'`, and the same frame, sniffing and referrer headers, so no page can frame the app and click in it. A reason is text or absent in every mode: the route and the agent both refuse anything else before it reaches an audit row, whose hash is computed over the value given while SQLite stores it as text.

## Budget arithmetic
Workers Free, per account and UTC day (verified on developers.cloudflare.com, 2026-10-15): 100,000 Worker requests (Workflow executions included); Durable Objects 100,000 requests (incoming WebSocket messages at 20 to 1), 100,000 SQLite rows written (deletes count as writes) and 5 GB stored; 100 concurrent Workflow instances. Static asset requests are free. The demo plans for half of each daily allowance, because the account is shared.

Durable Objects on Free also allow 5 million rows read a day and 13,000 GB-s of duration (wall-clock time while an object is active, at 128 MB; an idle object that may hibernate is not billed, and StaySignal's WebSockets are hibernatable). When an allowance runs out, further operations of that type fail until 00:00 UTC.

A request costs units: a read 1, a WebSocket upgrade 2, a write (POST) 12, a chat turn 18, the routine 80; a sandbox has 600 units. The measured upper bounds, asserted by `test/worker-public-demo/budget.test.ts`, are 5 Durable Object requests per unit (an upgrade and its 40 frames: 6 requests for 2 units), 2 rows written per unit, 300 rows written to seed a sandbox (117 measured, the memory store included), 50 rows read per unit (24 measured) and 400 to seed (158 measured), 250 ms of wall-clock time per unit while the Worker waits (at most 35 ms measured under the test runner, which is slower than production) and 4 MiB stored per sandbox (a measured tour: about 1.9 MiB with a conversation for each of the seven principals). The guided tour clicked through in the browser (`npm run test:e2e:public-demo`) spends about 375 of a sandbox's 600 units in about 165 Worker requests.

| Daily quantity | Bound | Demo budget |
|---|---|---|
| Worker requests | 15 sandboxes x 600 units = 9,000, plus 3 sign-in requests per sandbox | 50,000 |
| Durable Object requests | 15 x 600 x 5 = 45,000, plus 2 gate calls per sandbox | 50,000 |
| Rows written | 15 x 2 x (300 + 600 x 2) = 45,000 (the factor 2 counts the deletion at expiry) | 50,000 |
| Rows read | 15 x (400 + 600 x 50) = 456,000 | 2,500,000 |
| Duration | 15 x 600 x 0.25 s x 3 objects x 0.128 GB = 864 GB-s (every unit keeps three objects active for its whole wall-clock bound) | 6,500 GB-s |
| Stored bytes at any time | 10 live sandboxes x 4 MiB = 40 MiB | 1 GiB |
| Concurrent Workflow instances | 10 live sandboxes x 1 routine = 10 | 50 |

The table bounds admitted traffic. Refused traffic is bounded separately: a request without a valid cookie touches no Durable Object; a valid cookie whose sandbox refuses costs one Durable Object request per Worker isolate before the refusal is remembered; a chat request refused inside a conversation costs one request to the sandbox before that conversation remembers it.

`test/node/demo-budget.test.ts` recomputes this table from the constants and fails if any bound exceeds its budget.

## Consequences
On a busy day visitors see "The demo is busy, try again later" with a link to the README's walkthrough in screenshots; raising a cap means changing the constants and passing the arithmetic test. Residual risks, stated in the README:

- The daily cap of 15 sandboxes can be used up on purpose: one IPv4 address can start 3 an hour, and a handful of addresses (or /64 networks) can start all 15 in minutes, after which every visitor sees "busy" until 00:00 UTC, and 10 live sandboxes keep new visitors out for up to 4 hours. Keying IPv6 by /64 removes the cheapest form of it. Cloudflare Turnstile on sign-in, or a shared read-only showcase sandbox when the gate is full, would close it; both are deferred (Turnstile needs a widget created on the account, which builders do not create).
- Requests without a valid cookie still count toward the account's daily Worker requests (Cloudflare answers error 1027 when they run out, for every Worker on the account), and workers.dev hostnames get no WAF rate-limiting rule (a custom domain on a free zone allows one free rate-limiting rule in front of the Worker).
- The per-minute window of requests restarts when a sandbox object is evicted.
- CPU: the Durable Objects limits page lists 30 seconds of CPU per invocation for SQLite-backed objects, but its FAQ says objects have the same per-invocation CPU limits as Workers (10 ms on Free), and `wrangler dev` enforces neither. The review's V8 profiles under `wrangler dev` (2026-10-15) measured a sign-in at about 20 ms, a reset at about 40 ms (about 20 ms of it the seed's SQLite work inside the sandbox object), a chat turn at 44 to 146 ms and every page read at 1 to 6 ms. If the 10 ms reading applies, a sign-in fails, not only the chat; so the operator signs in once and runs one recorded chat turn on the deployed URL while `npx wrangler tail staysignal-demo --format json` runs, and reads each event's `cpuTime` and `outcome` (`exceededCpu`) before sharing the link (README, Public demo). Splitting the seed across invocations is the fallback.
- A browser that sends no `Sec-Fetch-Site` (Safari before 16.4) still sends `Origin` on every write and socket, so those stay refused from another origin; but an image or a navigation that another page on the account's subdomain starts carries the visitor's cookie with neither header, and spends a unit of their sandbox per request.
- One visitor drives every role, so separation of duties is shown between principals, not between people.

The demo's Worker logs one invocation in ten (`head_sampling_rate` 0.1, a deploy rule), so a flood of refused requests does not fill the account's Workers Logs.
