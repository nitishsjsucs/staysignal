# Data dictionary

Everything here describes the synthetic world of Larkspur Systems (`larkspur.example`). The extracts are generated by `staysignal world generate`; their schemas are in `sources/schemas/`, and a file that does not match its schema is never landed.

## Time

- Every source record carries an effective date (valid time) and `recorded_at` (knowledge time, UTC). A record is visible at vintage `v` when `recorded_at <= v` (ADR 0003).
- Spells are `[start_date, end_date)`: `end_date` is the first day not employed. A departure belongs to horizon `h` after cutoff `c` when `end_date` falls in `(c, c + h months]`.

## Extracts (`var/world/sources/`, landed under `var/landing/<source>/<period>/<sha256>.csv`)

| Extract | Raw table | Schema | Notes |
|---|---|---|---|
| `hris_records.csv`, `hris_delta_<date>.csv` | `raw.raw_hris` | `hris.schema.json` | the migration baseline and daily deltas at 06:00Z (possibly empty) |
| `payroll_<entity>_<period>.csv` | `raw.raw_payroll` | `payroll.schema.json` | one vendor file per entity and month; amounts as delivered |
| `ats_requisitions.csv`, `ats_offers.csv` | `raw.raw_ats_requisitions`, `raw.raw_ats_offers` | `ats.schema.json` | requisition events and offers |
| `org_teams.csv`, `org_events.csv`, `ref_bands.csv` | `raw.raw_org_teams`, `raw.raw_org_events`, `raw.raw_ref_bands` | `org.schema.json` | the organization tree (SCD2), reorganization events, pay bands |
| `audit_attributes.csv` | `audit.raw_audit_attributes` | `audit.schema.json` | the audit-only attribute (ADR 0013); never a feature, a dimension or part of a snapshot |

Every raw table adds `_batch_id`, `_file_sha256`, `_file_name` and `_loaded_at`. `raw._loads` lists each distinct file once; `raw._deliveries` lists every delivery, including an empty daily delta whose bytes repeat an earlier one (freshness, F01, is about deliveries).

## HRIS record fields

| Field | Meaning |
|---|---|
| `record_id` | `H` plus 8 digits; unique per delivered record |
| `employee_number` | `E` plus 6 digits; replaced by an `er_` key (HMAC) from staging onward |
| `record_type` | `migration_baseline`, `hire`, `rehire`, `promotion`, `transfer`, `team_change`, `manager_change`, `employment_type_change`, `termination`, `correction`, `rescission` |
| `effective_date` | when the change takes effect |
| `recorded_at` | when HRIS recorded it |
| `job_code`, `level`, `team_id`, `manager_employee_number`, `location_code`, `employment_type` | the assignment after the change |
| `contract_end_date` | the planned end of a fixed-term contract; needed for `fixed_term_days_remaining`, which the feature list of SPEC 6.4 omitted |
| `termination_reason_code` | `VOL_RESIGN` (voluntary), `INVOL_POSITION` and `INVOL_PERFORMANCE` (involuntary), `FT_END` (involuntary, end of a fixed-term contract), `RETIRE` (retirement) |
| `corrects_record_id` | for a `correction`, the record whose content it replaces; for a `rescission`, the termination it cancels |
| `source_batch_id` | the HRIS batch that carried the record |
| `legacy_hire_date`, `legacy_first_promotion_date`, `legacy_last_promotion_date` | on the migration baseline only: history from before 2023-04-01 |

Corrections and rescissions are resolved at each vintage from the records visible then: the latest visible correction of a record replaces its content, and a visible rescission removes the termination it cancels. A duplicate re-sends the same content under a new record ID and batch; only the first copy recorded is used (U01 counts the others).

## Payroll line fields

| Field | Meaning |
|---|---|
| `entity_code` | `US-ENT`, `CA-ENT`, `UK-ENT` |
| `pay_period` | `YYYY-MM` |
| `base_amount` | the vendor's amount, two decimals, in `currency` |
| `pay_basis_code` | the vendor's code; the dictionary in `payroll.schema.json` defines `M` (monthly amount) and `ANN` (annual amount) |
| `vendor_file_id`, `recorded_at` | the delivered file and its delivery time |

Mappings (`sources/mappings/payroll.v1.yaml`, `payroll.v2.yaml`) turn codes into annual multipliers and are applied downstream of staging, so every snapshot replays under any mapping version. `payroll@1` maps `M` and treats unknown codes as monthly; `payroll@2` adds `ANN` and rejects unknown codes.

## Warehouse layers (`warehouse/`, dbt on DuckDB)

| Layer | Schema | Models |
|---|---|---|
| staging | `staging` | `stg_hris__records` (typed, `er_` keys, content hash, `copy_no`), `stg_payroll__lines`, `stg_map__pay_basis` (the run's mapping), `stg_org__teams`, `stg_org__events`, `stg_ref__bands`, `stg_ats__requisitions`, `stg_ats__offers` |
| intermediate | `staging` | `int_hris__records_current` (as of the vintage), `int_hris__spell_records`, `int_hris__spells`, `int_hris__assignment_timeline` (SCD2), `int_hris__manager_timeline`, `int_hris__departures`, `int_comp__annualized`, `int_org__teams`, `int_org__team_events` |
| restricted | `restricted` | `fct_employee_month`, `fct_comp_position` (runner only; no predictions, ADR 0014) |
| published | `published` | `rpt_workforce_monthly` (cells under 10 suppressed), and the engine-written `forecast_runs` and `forecast_cohort` (cohorts of 10 or more only) |

The vintage and the payroll mapping are dbt variables (`vintage`, `pay_basis_mapping`) and part of every run manifest.
